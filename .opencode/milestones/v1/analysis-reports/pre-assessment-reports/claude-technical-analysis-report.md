# Atisse — Technical Debt & Architecture Risk Analysis Report

**Type:** Static code audit reference document (for AI agents)
**Scope:** `packages/core`, `packages/provider-*`, `packages/memory-*`, `packages/context-rag`
**Purpose:** Evidence-based findings list for future implementation agents (SPSA/SPBED/SPQAE) to reference when making decisions. Each finding includes file location, impact, and explicit remediation steps.

---

## 1. Shortcomings & Technical Debt

### 1.1 `pipeline.ts` Monolithic File Size

- **Location:** `packages/core/src/pipeline.ts` (1547 lines — the largest single module in the package, 3.4x the size of the next largest, `interfaces.ts`).
- **Issue:** Contradicts the "Small Core" principle (philosophy.md, Principle 7). Partial extraction was already done via milestones M002/M007 (`initializePipeline`, `executeToolRound`, `finalizePipeline`), but the file still hosts all flow-control logic for both streaming and non-streaming paths.
- **Impact:** Large blast radius — since both execution modes live in one file, a fix to one path risks breaking the other.
- **Remediation:**
  1. Split into `pipeline/shared.ts` (common helpers: `buildPromptRequest`, `handleOrchestratorError`, `resolveProfiles`), `pipeline/non-streaming.ts`, and `pipeline/streaming.ts`.
  2. Keep `executePipeline()` as the entry point in `pipeline/index.ts`, importing the two sub-modules.
  3. The public API (the `executePipeline` export) must remain unchanged — this is purely internal reorganization.

### 1.2 Code Duplication Between Streaming and Non-Streaming Paths (DRY Violation)

- **Location:** `executeGenerationRound` (~line 788) vs. `executeStreamingGenerationRound`; `executeToolRoundWithErrorHandling` (~line 717) vs. the streaming tool-retry block.
- **Issue:** Retry/backoff logic, fallback triggering, and tool-round counter management are nearly duplicated across both execution paths.
- **Impact:** A bug fix applied to one path may not be mirrored in the other, causing behavioral drift. Testing one path thoroughly does not guarantee correctness of the other.
- **Remediation:**
  1. Reduce the shared "execute one round" logic to a single generic function, parameterizing the output shape (chunks to yield vs. a direct response).
  2. Alternative: introduce a `RoundExecutionStrategy` interface (`onChunk`, `onComplete`) with two thin implementations for streaming/non-streaming, keeping the main loop in one place.

### 1.3 Excessively Long Positional Parameter Lists

- **Location:** `executeGenerationRound`, `executeStreamingGenerationRound`, `executeToolRound`, `finalizePipeline` — 12–15 positional parameters per function.
- **Issue:** Highly error-prone to parameter ordering (e.g., two adjacent `string` parameters can be swapped without the compiler catching it, since types match). Reduces readability and testability.
- **Impact:** Adding a new parameter requires updating every call site; refactoring cost is high.
- **Remediation:**
  1. Introduce a `PipelineRoundContext` object grouping the "stable" fields: `{ config, hooks, eventBus, logger, runId, stateMachine, trackDuration, input }`.
  2. Keep round-specific mutable state (`messages`, `toolAttempt`, `roundCounter`) as a separate second parameter.
  3. This reduces function signatures to 2 parameters and lets TypeScript's structural typing actually catch misuse.

### 1.4 Hardcoded Policy Values (Violates "Config Over Code")

- **Location:** `packages/core/src/pipeline.ts:255-256` — `CONTEXT_MAX_MESSAGES = 50`, `CONTEXT_MAX_CHARS = 50_000`.
- **Issue:** Violates the project's own Principle 5 ("Config Over Code") — these limits are module-level constants, not part of `ResolvedConfig`.
- **Impact:** Users cannot override these limits; integrations with large context document sets are silently truncated (only a log warning is emitted, no error).
- **Remediation:** Move these into `OrchestratorConfig.contextPolicy` (e.g. `maxMessagesPerProvider`, `maxContentLengthChars`), following the same pattern as the other defaults in `policies.ts`.

### 1.5 Hand-Rolled JSON Schema → Zod Converter (Partial Spec Support)

- **Location:** `packages/core/src/tool-controller.ts` (lines 126-294), `jsonSchemaToZod` and its helpers.
- **Issue:** Does not support commonly used JSON Schema keywords: `$ref`, `additionalProperties`, `patternProperties`, array `minItems`/`maxItems`, `const`, `default`, or `type` arrays (nullable unions). On an unrecognized/missing `type`, it returns `z.never()` — **rejecting all input silently**, which means a valid tool schema falling outside this subset can cause every call to fail-fast with `ToolValidationError`.
- **Impact:** Tool definitions generated by an LLM (especially OpenAI/Anthropic function-calling schemas) that fall outside this subset will silently fail; users will see "tool doesn't work" with the root cause hidden behind a debug-level log.
- **Remediation:**
  1. Short term: when an unsupported keyword is detected, throw an explicit `ToolDefinitionError` (new, FATAL, config-time) instead of falling through to `z.never()`.
  2. Medium term: evaluate migrating to a mature library (e.g. `json-schema-to-zod`) to externalize maintenance burden.
  3. Until `$ref` support exists, document this explicitly in the README / `writing-adapters.md` under "Unsupported JSON Schema Keywords."

### 1.6 `RedisMemoryAdapter` Error Type Semantic Mismatch

- **Location:** `packages/memory-redis/src/index.ts:35-65` — `load`, `save`, and `clear` all throw `ContextLoadError` on failure.
- **Issue:** `save()` and `clear()` failures are not semantically "context load" failures; `core` already defines a `MemorySaveError` type (`errors.ts`) that the adapter doesn't use.
- **Impact:** `isRetryable()` and error-based observability (the `error.code` field in events) misclassify failures — a save error is logged as "context load failed," misleading root-cause analysis.
- **Remediation:** Wire `save`/`clear` catch blocks to `MemorySaveError`, keep `load` on `ContextLoadError` (already defined in `core` — just import and use it correctly).

## 2. Architectural Risks

### 2.1 Race Condition in `RedisMemoryAdapter.save()` (Data Loss Risk)

- **Location:** `packages/memory-redis/src/index.ts:43-50`.
- **Issue:** `save()` follows a read-modify-write (RMW) pattern: it first `load()`s existing messages, then concatenates `[...existing, ...messages]` and writes back via `setEx`. **Not atomic** — no Redis transaction (`MULTI`/`EXEC`) or optimistic lock (`WATCH`) is used.
- **Impact:** Two concurrent `run()` calls for the same `sessionId` (e.g. a double-click, or two different horizontally-scaled instances) can **silently overwrite** each other's writes. This directly contradicts ADR-004 ("two concurrent run() calls must not interfere with each other") and the "Stateless Core → horizontal scalability" claim: even though the kernel itself is stateless, the shared memory adapter's state breaks that guarantee.
- **Remediation:**
  1. Make the `GET` + `SETEX` atomic via Redis `MULTI`/`EXEC`, or
  2. Use an append-only data structure: `RPUSH` to append messages to a list with `EXPIRE` for TTL (append-only structurally eliminates the race, unlike read-modify-write).
  3. Until fixed, document this risk explicitly in `memory-redis/README.md` under a "Concurrency Caveats" section.

### 2.2 No Behavioral Contract Guarantee Across `MemoryAdapter` Implementations

- **Location:** `packages/memory-inmemory/`, `packages/memory-redis/` — independent test suites, no shared conformance test suite.
- **Issue:** Each adapter is tested in isolation. Interface-level guarantees — TTL behavior, concurrent `save()` semantics, `load()` behavior after `clear()` — are never verified to match between implementations.
- **Impact:** A user developing against `memory-inmemory` and switching to `memory-redis` in production (a common migration path) discovers behavioral differences at runtime — showing the Interface-First principle (ADR-002) is not fully enforced in practice.
- **Remediation:** Add a shared `runMemoryAdapterConformanceTests(adapterFactory: () => MemoryAdapter)` function under `packages/core/src/testing/`; have both adapter packages import and run it from their own test files (a "shared behavior" test pattern).

### 2.3 Inconsistent Test Coverage Thresholds

- **Location:** `vitest.base.config.ts` (baseline 60% lines) vs. `packages/core/vitest.config.ts` (70% lines+branches).
- **Issue:** `provider-openai` and `provider-anthropic`, which depend directly on external APIs, run at a lower (60%) threshold than core — yet these packages contain fragile, frequently-changing integration points like error-status mapping (`http-status-mapping`) and message conversion.
- **Impact:** When the OpenAI/Anthropic API schema changes, low coverage may fail to catch the resulting regression.
- **Remediation:** Raise the coverage threshold for `provider-openai` and `provider-anthropic` to match core (70% lines/branches); specifically target 90%+ branch coverage for `finish-reason-mapping` and `http-status-mapping`, since these are the source of error classification.

### 2.4 Node.js `>=24` Requirement — Operational Adoption Risk

- **Location:** `package.json:engines.node = ">=24"`.
- **Issue:** Node 24 is a relatively new major version as of this report. Many enterprise CI/CD images, serverless runtimes (AWS Lambda, Vercel Edge, etc.), and LTS-dependent infrastructure may not yet support it.
- **Impact:** Library adoption is constrained by the target user base's runtime infrastructure — a critical adoption blocker for a framework/kernel-style package.
- **Remediation:**
  1. Determine the actual minimum requirement (e.g. `crypto.randomUUID()` is available since Node 15+, `AbortSignal.any()` since Node 20+ — the real minimum is likely 20, and 24 may be unnecessarily strict).
  2. Lower the minimum to the newest LTS version (e.g. Node 22 LTS) if possible; if a Node 24-specific API is genuinely required, justify it explicitly in the README.

### 2.5 v1 Scope Limitations Are Not Sufficiently Visible to Users

- **Location:** ADR-015 (context provider partial failure is fail-fast), ADR-017 (`stream: true` + `fallbackProvider` forbidden together).
- **Issue:** These constraints are documented in `.opencode/rules/decision-log.md` but not surfaced clearly in the root `README.md` or `docs/getting-started.md`.
- **Impact:** A user who tries combining `stream: true` with `fallbackProvider` and hits `ConfigValidationError` has to dig into internal ADR documents to understand this is an intentional v1 limitation.
- **Remediation:** Add a "Known v1 Limitations" section to `docs/getting-started.md`, listing each constraint with its error code, rationale, and target version (v1.x.x) reference.

## 3. Improvement Opportunities

### 3.1 Enforce the Core/Adapter Boundary at the Lint Level

- **Current state:** Manually verified via grep that `core` does not import adapter packages — but this rule is enforced only by convention, not statically.
- **Recommendation:** Add `no-restricted-imports` (or `import/no-internal-modules`) from `eslint-plugin-import` to `packages/core/eslint.config.mjs`, rejecting imports from `@atisse/provider-*`, `@atisse/memory-*`, `@atisse/context-*` at build time. This makes ADR-002 independent of human discipline.

### 3.2 Shared `PipelineContext` Type Definition

- **Recommendation:** Alongside the 1.3 remediation, define this context type in an internal file (e.g. `pipeline/types.ts`) rather than `interfaces.ts`, keeping the public API surface unchanged while doing internal refactoring.

### 3.3 Observability: Idempotency Test After the Redis RMW Fix

- **Recommendation:** Once 2.1 is fixed, add a concurrent-`save()` stress test to the `memory-redis` test suite, following the pattern already established in `tests/integration/stress.test.ts` in core — this pattern exists in the project already, it just needs to be extended to memory adapters.

### 3.4 Explicit "Supported Subset" Contract for JSON Schema

- **Recommendation:** Narrow the `Tool.inputSchema` type in `interfaces.ts` from `Record<string, unknown>` to a type representing the supported subset (`SupportedJsonSchema`). This catches unsupported schema shapes (e.g. those containing `$ref`) at compile time, reducing the risk of silent runtime rejection.

### 3.5 Sustain the Milestone Documentation Discipline

- **Observation (positive):** The M001–M012 plans under `.opencode/milestones/` track past bugs (timer leaks, AbortController propagation, rate-limit remapping) with strong evidentiary rigor — a rare level of maturity.
- **Recommendation:** Convert each finding in this report (1.1–2.5) into its own `M0XX-*.md` implementation plan and run it through the existing SPSA → SPBED → user-approval workflow, preserving the established process discipline.
