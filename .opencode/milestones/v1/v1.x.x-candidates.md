# V2 Release Candidates

## @atisse/core — Feature Backlog for v2+

This document catalogs all features, improvements, and architectural changes that were
explicitly deferred from v1. Each entry includes its origin (ADR, implementation plan,
or interface annotation), the v1 constraint that blocked it, and the design consideration
that must be resolved before v2 implementation begins.

Items classified as `v1.x.x` below are backward-compatible (MINOR/PATCH) candidates that
can be delivered in any v1 release. Only items classified as `v2` require a MAJOR version
bump.

---

## Category 1 — Tool System

### 1.1 Parallel Tool Execution

**Status:** Deferred — v1 enforces serial-only execution. → **v1.x.x candidate**  
**Origin:** `roadmap.md` v2+ Boundary table; `constraints.md` v1 Scope Hard Limits.  
**v1 Constraint:** `allowParallelTools: true` throws `ConfigValidationError` at construction.  
**Description:** When an LLM returns multiple tool calls in a single response round, the
kernel currently executes them sequentially. Parallel execution would dispatch all tool
calls concurrently via `Promise.all()`, reducing total tool round latency for independent
tools.  
**Design Consideration:** Requires a revised `ToolController.executeRound()` contract,
clear semantics for partial failure (fail-fast vs. collect-all), and careful handling of
`ToolResult[]` ordering guarantees. The `allowParallelTools` field is already in the
`ToolPolicy` interface — activation is a behavioral change, not a contract change.

---

### 1.2 Typed Tool Generics

**Status:** Deferred — v1 uses `unknown` for `Tool.execute()` input and output.  
**Origin:** `roadmap.md` v2+ Boundary table; `interfaces-core.md` Tool Contracts comment.  
**v1 Constraint:** `execute(input: unknown): Promise<unknown>` — typed generics require
JSON Schema → TypeScript inference, which has no straightforward solution in v1.  
**Description:** Allow `Tool<TInput, TOutput>` generic typing so that adapter authors
receive compile-time safety on tool input and output shapes, eliminating the need for
manual `safeParse` inside every `execute()` implementation.  
**Design Consideration:** JSON Schema → TypeScript inference is the core challenge. Options
include runtime Zod schema attachment on the `Tool` interface or a codegen approach. This
is a MAJOR interface change — `Tool` signature modification breaks all existing adapter
code. Requires a migration path.

---

### 1.3 Structured `ToolValidationError.validationErrors`

**Status:** Deferred — v1 uses `string[]`. → **v1.x.x candidate** (Additive — no breaking change)  
**Origin:** `M1-decision-record.md` C2 Decision 2.  
**v1 Constraint:** `validationErrors: string[]` chosen for simplicity.  
**Description:** Replace `string[]` with a structured `ValidationError[]` type carrying
field path, constraint violated, and received value — enabling programmatic error handling
by callers rather than string parsing.  
**Design Consideration:** Additive change (new type + optional migration). Low breaking
surface if implemented as a new field alongside the existing `string[]`.

## Category 2 — Streaming

### 2.1 Streaming + Fallback Combination

**Status:** Deferred — forbidden in v1 (ADR-017). → **v1.x.x candidate**  
**Origin:** `decision-log.md` ADR-017; `roadmap.md` v2+ Boundary table.  
**v1 Constraint:** `stream: true` + `fallbackProvider` → `ConfigValidationError` at
`run()` entry.  
**Description:** When a provider fails mid-stream, the consumer has already received
partial output. A v2 recovery contract could define how the kernel signals mid-stream
failure (a terminal `{ type: 'error' }` chunk), allows the consumer to decide whether
to retry, and optionally restarts the stream from the fallback provider with the full
prompt (not attempting to continue from the partial output).  
**Design Consideration:** The partial output problem is fundamental. Two viable models:
(a) fail-and-signal — yield `{ type: 'error' }` and let the consumer restart; (b)
transparent-restart — kernel buffers the partial stream and retries from scratch on
the fallback, yielding a clean stream to the consumer. Model (b) has significant memory
and latency implications. The contract must be defined before implementation begins.

---

## Category 3 — Context Loading

### 3.1 Configurable Partial Context Failure (Best-Effort Mode)

**Status:** Deferred — v1 is fail-fast (ADR-015). → **v1.x.x candidate**  
**Origin:** `decision-log.md` ADR-015; `roadmap.md` v2+ Boundary table.  
**v1 Constraint:** First `ContextProvider` failure aborts all context loading. Partial
results from earlier providers are discarded.  
**Description:** A `contextPolicy.onProviderFailure: 'fail' | 'skip'` option would allow
users to configure the kernel to skip a failed provider and continue with results from
the remaining providers. The `context.failed` event would still fire for observability.  
**Design Consideration:** Silent partial context is a correctness risk — LLM output
quality depends on context completeness. The API must make the trade-off explicit.
`contextPolicy` is currently internal-only and not exposed in `OrchestratorConfig`.
Exposing it is a MINOR additive change.

---

## Category 4 — Policy & Configuration

### 4.1 `contextTimeoutMs` in `TimeoutPolicy`

**Status:** Deferred — v1 relies on `totalTimeoutMs` as a ceiling for context loading. → **v1.x.x candidate**  
**Origin:** `M1-decision-record.md` B5 Decision 3.  
**v1 Constraint:** Not added — `totalTimeoutMs` was deemed sufficient.  
**Description:** A dedicated `contextTimeoutMs` field in `TimeoutPolicy` would allow
fine-grained timeout control per context loading phase, independent of the total run
ceiling. Useful when context providers have known SLA characteristics (e.g., a RAG
vector store with a 2s target) that should not consume the entire `totalTimeoutMs`
budget.  
**Design Consideration:** Additive optional field — backward-compatible MINOR change.
`ContextProvider.provide()` would need an `AbortSignal` injected, mirroring ADR-014's
approach for provider calls.

---

### 4.2 `jitterFactor` in `RetryPolicy`

**Status:** Deferred — v1 exposes only `jitter: boolean`. → **v1.x.x candidate**  
**Origin:** `M1-decision-record.md` B5 Decision 2.  
**v1 Constraint:** The 30% partial jitter algorithm is an implementation detail in
`policies.ts`, not a frozen contract.  
**Description:** Replace `jitter: boolean` with `jitter: boolean | { factor: number }`
or a separate `jitterFactor?: number` field (range 0–1), giving callers control over
the randomness magnitude applied to retry delays.  
**Design Consideration:** The current `jitter: boolean` field is frozen. Options:
(a) add an optional `jitterFactor?: number` alongside the boolean (additive, MINOR);
(b) widen `jitter` to a union type (potentially breaking for strict consumers). Option
(a) is preferred.

---

## Category 5 — Observability

### 5.1 Logger Injection into `EventBus`

**Status:** Deferred — v1 silently swallows listener errors. → **v1.x.x candidate**  
**Origin:** `M1-decision-record.md` E3 Decision 2.  
**v1 Constraint:** Listener errors silently swallowed in V1. `EventBus` Logger injection
is V2 candidate.  
**Description:** Allow an optional `Logger` to be injected into `EventBusImpl`, so that
swallowed listener errors are at minimum logged at `warn` level rather than disappearing
entirely. This closes a debuggability gap where a failing event listener is invisible
to the operator.  
**Design Consideration:** `EventBus` is an internal interface — not exposed in
`OrchestratorConfig`. Logger is already available in the `Orchestrator` constructor.
Wiring it through to `EventBusImpl` is a low-risk internal change requiring no
interface modification.

---

### 5.2 Built-In Logger Implementation

**Status:** Deferred — v1 default is a no-op logger. → **v1.x.x candidate**  
**Origin:** `M1-decision-record.md` B8 Decision 4; `interfaces-runtime.md` Logger Contract.  
**v1 Constraint:** No built-in logger — production deployments must inject their own.  
**Description:** Ship a structured JSON logger as a named export (`JsonLogger`,
`PrettyLogger`) that users can opt into without wiring their own implementation.
Should respect the `Logger` interface exactly and support log level filtering via a
constructor option.  
**Design Consideration:** Must not introduce any Node.js-specific APIs that break
runtime-agnostic compatibility (`lib: ["ES2022"]`). Output transport (stdout vs.
file) should be pluggable.

---

## Category 6 — Architecture & Performance

### 6.1 WASM / Rust Core

**Status:** Deferred — v1 is pure TypeScript. → **v1.x.x candidate**  
**Origin:** `roadmap.md` v2+ Boundary table.  
**v1 Constraint:** Not applicable — performance optimization track, not a v1 goal.  
**Description:** Rewrite performance-critical kernel internals (state machine evaluation,
policy computation, prompt token estimation) in Rust, compiled to WASM, and loaded by
the TypeScript surface layer. The public `Orchestrator` API would remain unchanged.  
**Design Consideration:** The token estimation function (`Math.ceil(text.length / 4)`)
is the most obvious candidate. Real tokenizer accuracy is also a v2 candidate (see 6.2).
Full WASM core is a significant engineering investment requiring benchmarks to justify.

---

### 6.2 Accurate Token Estimator

**Status:** Deferred — v1 uses the `length / 4` approximation. → **v1.x.x candidate**  
**Origin:** `M1-decision-record.md` D3 Decision 3; `prompt-composer.ts` inline comment.  
**v1 Constraint:** Real tokenizers are external dependencies, incompatible with the
runtime-agnostic design constraint.  
**Description:** Replace `Math.ceil(text.length / 4)` with a proper tokenizer (e.g.,
`tiktoken` for OpenAI models, Anthropic's tokenizer for Claude). The `PromptComposer`
memory trimming logic would become significantly more accurate, reducing both
over-trimming and context window overflow.  
**Design Consideration:** Tokenizer is model-specific. The `AIProvider` interface could
expose an optional `estimateTokens?(text: string): number` method, allowing each adapter
to provide accurate counting. The core would fall back to the approximation when the
method is absent.

---

### 6.3 Redis Atomic Memory Writes (WATCH/MULTI/EXEC)

**Status:** Deferred — v1 uses a read-modify-write pattern. → **v1.x.x candidate**  
**Origin:** `M4-implementation-plan.md` D-M4-8 note.  
**v1 Constraint:** `RedisMemoryAdapter` uses `GET` + `SETEX` — race condition risk under
concurrent writes to the same session is documented and accepted.  
**Description:** Replace the read-modify-write pattern with Redis `WATCH/MULTI/EXEC`
transactions to guarantee atomicity under concurrent `run()` calls sharing a `sessionId`.
**Design Consideration:** `redis` client v5 supports transactions. The `MemoryAdapter`
interface requires no change — this is an internal `RedisMemoryAdapter` improvement.
The v1 sequential-within-session guarantee (single-user sessions) may render this
unnecessary for most use cases.

## Category 7 — Out-of-Scope for v2 (Framework Territory)

The following items are explicitly **not** v2 candidates. They represent scope boundaries
that define what this project is not — crossing them would transform the kernel into a
framework.

| Feature                         | Reason                                         |
| ------------------------------- | ---------------------------------------------- |
| Agent planning loop             | Autonomous decision-making — different product |
| Multi-agent communication       | Agent-to-agent protocol — different product    |
| Workflow DAG / step chaining    | Pipeline engine scope — different product      |
| Visual editor / no-code UI      | Not a UI project                               |
| SaaS dashboard / cost analytics | Not a SaaS                                     |
| Distributed orchestration       | Infrastructure concern outside kernel scope    |

These boundaries are governed by `philosophy.md` Principle 3 (Kernel, Not Framework)
and `constraints.md` v1 Scope Hard Limits. Revisiting any of them requires a formal
architectural review and explicit user approval before any scoping discussion.
